# 第 4 步：坐标系约定

实验脚本：[step4_axes.py](step4_axes.py)

```bash
pixi run python docs/learn/step4_axes.py
```

第 2 步讲了"同一个点在不同坐标系下有不同的坐标"。这一步讲不同软件和文件格式各自约定了怎样的世界坐标系，以及数据在它们之间流动时坐标怎样变化。之前发现的 benchmark bug 就出在这里。

## 1. 一个世界坐标系需要约定哪几件事

三根轴本身只是三个互相垂直的方向。要让不同软件对同一份数据得出相同的理解，还需要约定：

| 约定 | 含义 | Blender | glTF |
|---|---|---|---|
| 向上的轴 | 哪根轴指向"天" | **+z** | **+y** |
| 正面朝向 | 物体的"正面"默认朝哪根轴 | −y | +z |
| 手性 | 右手系还是左手系 | 右手系 | 右手系 |
| 单位 | 坐标值 1 代表多长 | 1 米（默认） | 1 米（规范规定） |

**手性**（handedness）的意思是：伸出右手，拇指指向 +x、食指指向 +y，中指自然弯曲所指的方向如果是 +z，就是右手系；用左手才对得上就是左手系。两种手系互为镜像，不能只靠旋转互相转换。Blender 和 glTF 都是右手系，所以它们之间只差一个旋转。

## 2. 同一张书桌，两种坐标系下的尺寸

实验第 1 部分分别读取 glTF 文件里的原始坐标（第 3 步的解析方法，加上节点平移）和 Blender 导出的 NPZ 坐标：

```
glTF 文件（y 向上）          尺寸 x=0.745 y=0.729 z=1.184   最长轴 z，最短轴 y
Blender 导出 NPZ（z 向上）   尺寸 x=0.745 y=1.184 z=0.729   最长轴 y，最短轴 z
```

桌子高 0.729 米。在 glTF 里，高度出现在 y 这一列；在 Blender 里，高度出现在 z 这一列。桌面长边 1.184 米，在 glTF 里沿 z 方向，在 Blender 里沿 y 方向。

## 3. 转换矩阵：用第 2 步的换基底来理解

Blender 导入 glTF 时，会自动把坐标从 glTF 的坐标系换算到 Blender 的坐标系。按第 2 步的说法，这是换基底：书桌本身没有动，只是换了一组基底来描述它。换算矩阵的第 j 列，就是 glTF 的第 j 根轴在 Blender 坐标系下的坐标：

| glTF 的轴 | 物理含义 | 在 Blender 坐标系下 |
|---|---|---|
| +x | 右 | (1, 0, 0)，即 +x |
| +y | 上 | (0, 0, 1)，即 +z |
| +z | 正面 | (0, −1, 0)，即 −y |

把这三列排在一起：

```
          | 1  0   0 |
    P  =  | 0  0  −1 |          [v]_Blender = P [v]_glTF
          | 0  1   0 |
```

也就是：x 不变，Blender 的 y = −glTF 的 z，Blender 的 z = glTF 的 y。实验第 2 部分验证了这一点：

```
行列式: 1 （+1 表示是旋转，不是镜像）
转换后与 NPZ 的最大误差: 0.0
不转换直接比较的最大误差: 0.957
```

用 P 换算 glTF 的坐标，结果和 Blender 导出的 NPZ **逐个顶点完全相同**。不换算直接比较，误差接近 1 米。

**行列式为什么重要**：行列式 +1 表示 P 是一个旋转（这里是绕 x 轴转 90°），手性保持不变。如果有人写成"y 和 z 直接互换、不加负号"，行列式就是 −1。那是一个镜像，会把物体左右翻转，比如一个右旋的螺旋楼梯会变成左旋的。

## 4. 在本项目里，坐标在哪些地方被换算

| 环节 | 读写方式 | 坐标系 |
|---|---|---|
| 目标 GLB 文件 | — | glTF，y 向上 |
| 数据准备：`import_glb.py` 用 Blender 导入 GLB | Blender 自动换算 | Blender，z 向上 |
| 目标 NPZ | `export_mesh.py` 导出 | Blender，z 向上 |
| 模型生成的脚本 | 直接在 Blender 里建模 | Blender，z 向上 |
| 生成结果 NPZ | `export_mesh.py` 导出 | Blender，z 向上 |

奖励比较的两份 NPZ 都在 Blender 坐标系下，向上的轴都是 z，所以本项目的奖励不存在坐标轴不一致的问题。这也是第 2 步提到的"目标和生成结果走同一条 Blender 流程"的好处。

单位方面，两边都是米。目标是真实世界的尺寸（书桌桌面长 1.18 米），而模型在 Blender 里写 `size=1` 就是 1 米。参考图里看不出绝对尺寸（第 5 步讲），所以模型很难猜对这个尺度。

## 5. benchmark 读取 GLB 的方式不同

3DHarnessBench 的 `shape_chamfer.py` 不经过 Blender，而是用 trimesh 直接读取 GLB。trimesh 不做坐标轴换算，读进来的坐标仍然是 glTF 坐标系，y 向上。它的 `cd_yawmin` 却按"z 向上"的假设，绕 z 轴旋转物体。

实验第 3 部分把"绕 z 轴转 90°"分别作用在两种坐标系下的书桌上：

```
Blender 坐标（z 向上）   尺寸 x=1.184 y=0.745 z=0.729   最长轴 x，最短轴 z
glTF 坐标（y 向上）      尺寸 x=0.729 y=0.745 z=1.184   最长轴 z，最短轴 x
```

请对照第 2 节的原始尺寸，自己判断这两次旋转分别对书桌做了什么。

## 和奖励的关系

1. 本项目的目标和生成结果都在 Blender 坐标系下比较，坐标轴是一致的。
2. 如果以后奖励要直接读 GLB，或者要复用 benchmark 的代码，必须先确认坐标系，否则"绕竖直轴旋转"会变成别的旋转。
3. 尺度以米为单位，是真实世界的尺寸。这对模型来说是一个很难从图片里获得的信息，第 5 步和第 8 步会继续讨论。

## 检验问题

1. 根据第 3 部分的输出，benchmark 的 `cd_yawmin` 为什么是错的？`cd_axismin` 在全部 24 个轴对齐旋转里取最小值，它为什么不受影响？
2. 如果把转换矩阵错写成"x 不变、y 和 z 直接互换"，书桌的包围盒尺寸和正确转换的结果完全一样。那么错在哪里？为什么只看包围盒发现不了这个错误？

## 解答

**问题 1**：trimesh 读入的坐标是 y 向上，`cd_yawmin` 却绕 z 轴旋转。实验第 3 部分里，glTF 坐标下的书桌转完之后，高度 0.729 从 y 列跑到了 x 列，也就是书桌被放倒了，而不是水平转向。所以 `cd_yawmin` 比较的不是"四个水平朝向"，名字和实际含义不符。`cd_axismin` 枚举全部 24 个轴对齐旋转，其中包含真正绕 y 轴（glTF 的竖直轴）的 4 个水平旋转，所以取最小值时不受影响。

**问题 2**："y 和 z 直接互换"的矩阵行列式是 −1，它不是旋转，而是**镜像**：物体会变成原来的镜中像，手性被翻转。

包围盒看不出来，是因为包围盒只记录每根轴方向上的范围。镜像只是把某根轴的正负方向对调，范围的长度不变，所以包围盒尺寸完全一样。书桌本身左右对称，镜像之后连形状都和原来重合，任何指标都看不出差别。但对于不对称的物体，镜像就是另一个形状，比如右旋的螺旋楼梯会变成左旋的。

这也解释了 benchmark 的 24 个旋转为什么只保留行列式为 +1 的：镜像会改变物体的形状，不应该被当作"同一个物体换了个朝向"而原谅。
