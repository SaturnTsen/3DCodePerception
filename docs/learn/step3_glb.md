# 第 3 步：GLB 文件里装了什么

实验脚本：[step3_glb.py](step3_glb.py)

```bash
pixi run python docs/learn/step3_glb.py
```

数据集里每个物体的目标形状都存成 GLB 文件。这一步不借助任何 3D 库，直接按格式规范把书桌的 GLB 拆开，看清楚里面有什么，以及奖励实际用到了哪一部分。

## 1. glTF 和 GLB 是什么关系

**glTF** 是一种通用的 3D 场景交换格式，用来在不同软件之间传递模型。它把内容分成两部分：

- 一段 **JSON**，描述结构：有哪些节点、网格、材质，每个数组在哪里、是什么类型。
- 一段**二进制数据**，存放真正的数字：顶点坐标、三角形下标、贴图图片等。

**GLB** 是把这两部分打包成一个文件的二进制版本。文件结构很简单：

```
12 字节文件头（magic = "glTF"、版本号、总长度）
JSON 块：结构描述
BIN 块：原始数组字节
```

书桌 GLB 的实测结果：

```
文件头: magic=b'glTF' version=2 总长度=139832 字节
  块 b'JSON': 3416 字节
  块 b'BIN\x00': 136388 字节
```

JSON 只有 3 KB，绝大部分体积是二进制数据。

### 逐字节看文件开头

文件头之后，数据按**块**（chunk）依次排列。每个块由两部分组成：8 字节的**块头**，加上块的内容。块头只记录两件事：内容有多少字节，内容是什么类型（`JSON` 或 `BIN\0`）。读取程序先读块头，就知道接下来多少字节属于这个块、该怎样解析，读完这么多字节就到了下一个块的开头。所以"JSON 块头"就是 JSON 块前面的这 8 个字节。

GLB 里的整数都是 4 字节无符号整数，按**小端序**存储（低位字节在前）。在 JSON 正文开始之前，一共有 **20 个字节**的头部信息，分成两段：12 字节的文件头，加上 JSON 块自己的 8 字节块头。下面是一个 GLB 文件的前 21 个字节：

| 偏移 | 字节 | 含义 |
|---|---|---|
| 0–3 | `67 6C 54 46` | 文件头：magic，ASCII 字符 `glTF` |
| 4–7 | `02 00 00 00` | 文件头：版本号 2 |
| 8–11 | `F8 4E 04 00` | 文件头：整个文件的长度，0x00044EF8 = 282360 字节 |
| 12–15 | `0C 0D 00 00` | JSON 块头：块内容的长度，0x0D0C = 3340 字节 |
| 16–19 | `4A 53 4F 4E` | JSON 块头：块类型，ASCII 字符 `JSON` |
| 20 | `7B` | JSON 正文的第一个字符 `{` |

JSON 正文结束后，紧接着是 BIN 块，格式相同：4 字节长度、4 字节类型 `BIN\0`，然后是数据本身。规范要求每个块的长度是 4 的倍数，不足时 JSON 块用空格补齐，BIN 块用零补齐。

## 2. JSON 里的层级：从场景一路指到字节

JSON 里的对象互相用**下标**引用，形成一条链：

| 层级 | 作用 | 书桌里的内容 |
|---|---|---|
| scene（场景） | 列出根节点 | 只有节点 0 |
| node（节点） | 相当于第 2 步的"对象"：引用一个网格，并带有自己的变换 | `simple_desk_top`，平移 `[0, -0.3646, 0]` |
| mesh（网格） | 由若干个**图元**（primitive）组成，每个图元是一组三角形，配一种材质 | 2 个图元：桌面、桌腿 |
| accessor（访问器） | 说明一个数组的元素类型和形状，例如"1536 个 float32 三元组" | 每个图元 4 个：位置、法线、贴图坐标、三角形下标 |
| bufferView（缓冲视图） | 说明这个数组在 BIN 块里从第几个字节开始、有多长 | — |

读取顶点坐标的过程就是顺着这条链走：图元的 `POSITION` 属性 → 访问器 → 缓冲视图 → BIN 块里的一段字节 → 用 NumPy 按 float32 解释成 N×3 数组。脚本里的 `read_accessor` 就做这件事。

## 3. 书桌 GLB 的实际内容

```
节点: {'mesh': 0, 'name': 'simple_desk_top', 'translation': [0, -0.3646, 0]}
  图元 0: 材质 0，属性 ['POSITION', 'NORMAL', 'TEXCOORD_0']，顶点 24，三角形 12
    局部坐标范围 min [-0.373  0.7   -0.592] max [0.373 0.729 0.592]
  图元 1: 材质 1，属性 ['POSITION', 'NORMAL', 'TEXCOORD_0']，顶点 1536，三角形 1008
    局部坐标范围 min [-0.342  0.    -0.561] max [0.342 0.7   0.561]
合计: 顶点 1560，三角形 1020
```

可以读出几件事：

1. **整张书桌是一个节点、一个网格。** 图元 0 是桌面：一个扁平的长方体，24 个顶点、12 个三角形。图元 1 是桌腿和框架，四条腿已经合并成一份网格，没有第 2 步说的"共用网格数据"。生成这些 GLB 时，修改器和共用关系都已经展开成了真实几何。
2. **合计的数字和第 1 步对得上。** 第 1 步从 NPZ 里读到的是 1560 个顶点、1020 个三角形，正是这两个图元相加的结果。
3. **第 2 步讲的变换在这里也出现了。** 图元里存的是局部坐标，竖直方向的范围是 0 到 0.729，也就是桌腿底部在 0。节点的平移量是 −0.3646，正好是高度的一半。乘上节点变换之后，世界坐标的竖直范围变成 ±0.365，包围盒中心落在原点。这就是第一次审查时看到的"包围盒中心对齐原点"的来源。
4. **竖直方向在 glTF 里是第二根轴（y）。** 上面的高度范围出现在 y 那一列，而第 1 步的 NPZ 里同样的范围出现在 z 那一列。原因是 glTF 规定 y 轴向上，Blender 规定 z 轴向上，Blender 的导入器自动做了转换。这一点第 4 步专门讲。

### 图元和材质

**材质**（material）是一组描述"表面看起来什么样"的参数：底色、金属感、粗糙程度、有没有清漆涂层，以及要贴哪些贴图图片。JSON 的 `materials` 数组里每一项就是一种材质，书桌有两种：材质 0 是桌面的白色，材质 1 是桌腿的黑色金属。"一种材质"指的就是这个数组里的一项。

**网格和图元是"容器"和"内容"的关系。**

- **网格**（mesh）是一个整体形状，也是节点引用的单位。它自己**不存任何几何数据，也没有变换**，只是一个装图元的列表。
- **图元**（primitive）是网格里真正存数据的单位。每个图元都是一份完整、独立的三角网格：有自己的顶点数组（`attributes`）、自己的三角形下标数组（`indices`），并指定一种材质（`material`）。

书桌 JSON 的骨架（省略了无关字段）：

```json
"nodes":  [ { "name": "simple_desk_top", "mesh": 0, "translation": [0, -0.3646, 0] } ],
"meshes": [ { "primitives": [
              { "attributes": { "POSITION": 0, ... }, "indices": 3, "material": 0 },
              { "attributes": { "POSITION": 4, ... }, "indices": 7, "material": 1 }
          ] } ],
"materials": [ { "name": "...DeskTop_White..." }, { "name": "...DeskLeg_BlackMetallic..." } ]
```

画成层级就是：

```
节点 0（带变换：平移 −0.3646）
└── 引用 网格 0（只是一个列表，无数据、无变换）
    ├── 图元 0：24 个顶点、12 个三角形   ── 引用 → 材质 0（白色）
    └── 图元 1：1536 个顶点、1008 个三角形 ── 引用 → 材质 1（黑色金属）
```

各层之间的引用规则：

| 关系 | 规则 | 含义 |
|---|---|---|
| 节点 → 网格 | 一个节点最多引用一个网格；一个网格可以被多个节点引用 | 第 2 步的"共用网格数据"在 glTF 里就是这样表达的 |
| 网格 → 图元 | 图元直接写在网格内部，不能被其他网格引用 | 图元只是网格的组成部分，不能单独摆放 |
| 图元 → 材质 | 每个图元引用一种材质；一种材质可以被多个图元引用 | 材质单独存放，供多处共用 |

**两种视角来看整体结构。**

- **层级视角**：场景 → 节点树，负责"东西摆在哪里"。节点之间还可以有父子关系（`children` 字段），子节点的世界变换 = 父节点的世界变换 @ 子节点自己的变换；书桌只有一个节点，所以这里看不出来。网格 → 图元，负责"一个形状由哪几组三角形组成"。
- **资源视角**：网格、材质，以及更底层的访问器、贴图、图片，都是放在顶层数组里的独立资源，别人通过下标引用它们。节点引用网格，图元引用材质和访问器，材质引用贴图，贴图引用图片。同一份资源可以被多处引用，所以共用是天然支持的。

从 JSON 的写法上看，除了图元直接写在网格内部，其他所有东西（包括场景引用的节点）都是顶层数组加下标引用。Blender 也是同样的划分：对象相当于节点，网格数据和材质是可以被多个对象共用的资源。

**为什么要分两层？** 两层各管一件事：

- **网格这一层管"一起摆放"**：节点的变换作用在整个网格上，网格里的所有图元一起平移、旋转、缩放。桌面和桌腿属于同一张桌子，必须一起移动。
- **图元这一层管"按材质分组"**：一个三角形只能有一种材质，显卡一次绘制调用也只能设置一套材质参数。所以同一个网格里用到几种材质，就要拆成几个图元，每个图元对应一次绘制调用。

**和 Blender 的对应关系。** Blender 的网格数据是一个整体：只有一套顶点数组，每个面记录自己用哪个材质槽位。导出 glTF 时，导出器按材质槽位把面分组，每组生成一个图元，并把这组面用到的顶点**复制**进该图元自己的顶点数组。因此：

- 位于两种材质交界处的顶点，会在两个图元里各存一份。
- 每个图元的下标都从 0 开始，只在本图元内部有效。脚本把两个图元合并成一个网格时，要给图元 1 的下标加上图元 0 的顶点数 24，否则图元 1 的三角形会指到图元 0 的顶点上。
- 反过来，Blender 导入 glTF 时，会把同一个网格的所有图元合并回一份网格数据，每个面记住自己的材质槽位。

灰色版 GLB 也是 2 个图元，虽然它的两种材质都变成了同样的灰色。原因是图元按材质槽位划分，而不是按外观是否相同划分。

对奖励来说，图元的划分没有影响：导出 NPZ 时，所有图元的三角形都会合并成一个网格。

## 4. 每个顶点不止有坐标

图元的属性有三项：

| 属性 | 含义 | 奖励用不用 |
|---|---|---|
| `POSITION` | 顶点坐标 | 用 |
| `NORMAL` | 法线，即表面在这个顶点朝外的方向，用于计算光照明暗 | 不用 |
| `TEXCOORD_0` | 贴图坐标，表示这个顶点对应贴图图片上的哪个位置 | 不用 |

第 1 步看到"同一位置存了好几个重复顶点"，原因就在这里：桌面的一个角同时属于顶面、侧面和正面，三个面的法线不同，所以要存三份坐标相同、法线不同的顶点。

## 5. 材质和贴图

彩色版 GLB 有 2 个材质和 4 张贴图图片：

```
材质: ['simple_desk_top_DeskTop_White.001_pbr_baked', 'simple_desk_top_DeskLeg_BlackMetallic.001_pbr_baked']
贴图图片: [... coat_weight ..., ... normal ..., ... base_color ..., ... metallic ... roughness ...]
```

**材质**描述表面看起来是什么样子：颜色、金属感、粗糙程度、有没有清漆涂层。**贴图**是一张图片，按贴图坐标"贴"到表面上，让颜色和质感可以逐点变化。名字里的 `baked`（烘焙）表示这些贴图是从原始的程序化材质计算出来的结果。

## 6. 彩色版和灰色版的区别

每个物体有两个 GLB：`SimpleDeskFactory.glb`（彩色版）和 `SimpleDeskFactory_grey.glb`（灰色版）。脚本逐字节比较了两者的几何：

```
彩色版和灰色版的顶点完全相同: True
彩色版和灰色版的三角形完全相同: True
```

两者的**几何完全相同**，区别只在材质：灰色版去掉了全部贴图，两种材质都换成统一的灰色（`baseColorFactor` 0.55）。所以灰色版文件小得多（58 KB 对 140 KB）。

在本项目里：

- 数据准备读取的是彩色版 GLB（`rl/data_prep/threed_code_data_factory.py:69`）。由于几何相同，换成灰色版得到的目标网格也完全一样。
- 给模型看的参考图用的是 `color_renders/`，也就是彩色版渲染的图（`configs/data-3d_code_data_factory.yaml:3-7`）。

## 和奖励的关系

GLB 里装了节点树、几何、法线、贴图坐标、材质、贴图。经过 `import_glb.py` 和 `export_mesh.py` 之后，进入 NPZ 的只有两样东西：**世界坐标下的顶点位置和三角形下标**。法线、贴图坐标、材质、贴图全部被丢掉。

模型生成的脚本也走同一条导出流程，所以它写的材质代码同样不会进入奖励计算。

## 检验问题

提示词要求模型重建材质和纹理。这些材质代码对奖励有没有影响？如果有，是通过什么途径产生影响的？

## 解答

材质本身不影响奖励，这一点正确：材质信息在导出 NPZ 时被丢掉了。占用回答长度也是对的，而且这是最主要的一条间接途径。完整地看，材质代码有三条途径间接影响奖励，都是通过"让脚本得不到有效几何"：

1. **挤占回答长度**：材质节点代码很长。回答达到 `max_response_length`（4096 token）被截断后，脚本不完整，Python 报语法错误，几何一个都不会生成，奖励为 0。
2. **自身出错**：材质节点的名字、接口在不同 Blender 版本之间常有变化。材质代码里只要有一行报错，整个脚本就中断，前面建好的几何也不会被导出，奖励同样为 0。
3. **拖慢执行**：如果材质代码里有烘焙之类的耗时操作，可能超过奖励端 60 秒的超时，结果同样是 0 分。

还有一个训练层面的后果：GRPO 按整条回答的奖励更新所有 token，材质 token 得到的梯度信号完全来自形状好坏，和材质写得对不对无关。时间长了，模型可能学会少写或不写材质，这和提示词的要求相互矛盾。这就是之前建议从提示词里删掉外观要求的原因。
