# 待办事项

记录截至 2026-11-18 尚未决定或尚未处理的事项，按依赖顺序排列：前面的决定会影响后面的实施。依据见 `docs/learn/` 下各步的讲解和实验。

## 一、奖励设计（需要决定）

### 1. 提示词与新奖励保持一致

奖励已经不再对位置和整体尺度扣分（见"已完成"）。提示词里的 "Place the object at the origin" 和 "absolute scale ... choose reasonable defaults" 是否需要调整，还没有决定。

### 2. 撒点方式

- **现状**：按面积均匀撒点，每个部位的权重等于面积占比，细小部件的错误被稀释。删掉一条桌腿，腿上的点平均误差 37.1 厘米，但只占 3.88% 的权重（[第 7 步](learn/step7_chamfer.md)）。
- **选项**：保持按面积撒点；或者改成按部件分配点数；或者改用平方距离放大远处的点。
- **建议**：先保持按面积撒点。训练中如果观察到模型经常漏掉细小部件，再处理。
- **未验证**：目标网格能否可靠地按"三角形是否相连"拆出部件。

### 3. 奖励的温度和权重

- **现状**：奖励由四个分量加权求和：Chamfer 分量 exp(−d/τ)、DINOv3 相似度、Uni3D 点云与点云相似度、Uni3D 点云与参考图相似度。执行失败得 0 分。τ 和四个权重已经写在 YAML 里，但都是占位值（τ = 1，各权重 0.25）。
- **依据**：一组回答里只要有一个失败，成功回答之间的差异就几乎不产生学习信号（[第 9 步](learn/step9_reward.md)）。一个分量对 GRPO 的实际影响约等于"权重 × 它在组内的波动幅度"。点云与参考图的相似度只在 0.2 到 0.4 之间变化，等权重时影响偏小。τ = 1 时，形状无关的物体 Chamfer 分量仍有约 0.68。
- **做法**：用初始模型对一批训练样本生成回答，统计执行成功率和各分量在组内的波动幅度，再确定 τ 和权重。

### 4. Blender 版本号和运行预算的写法

提示词现在写的是 Blender 5.1 和 60 秒运行预算，和本项目的实际环境一致。benchmark 的原文是 Blender 5.0 和 240 秒。是否恢复成 benchmark 的原文，还没有确认。

## 二、训练配置（需要决定）

### 5. LoRA 还是全量训练

- **现状**：训练配置没有写 `lora_rank`，按 verl 默认值 0 运行，实际是全量训练，也违反了"训练参数必须在 YAML 中显式填写"的约定。
- **建议**：LoRA，`lora_rank: 64`、`lora_alpha: 128`、`target_modules: all-linear`，冻结视觉编码器，学习率从 1e-6 调到 1e-5 量级。

### 6. 分布式方案

- **建议**：保持 FSDP2。27B 模型用 DDP 时单卡放不下，verl 也不提供 DDP 训练后端。

### 7. 硬件规格

- 需要提供 H100 机器的卡数。卡数决定 vLLM 的张量并行规模、batch 大小和 `n_gpus_per_node`。

## 三、需要先验证的风险

### 8. Qwen3.5 的 LoRA 兼容性

Qwen3.5 有部分层是线性注意力（Gated DeltaNet）。还不确定 verl 的 LoRA 能否作用到这些层，以及 vLLM 能否加载这些层上的 LoRA。上 H100 之前，先在本机用同架构的小模型跑几步验证。

### 9. 本机内存

本机（2 张 A6000、内存 125 GB）跑 9B 全量训练，估算内存需求约 90 GB，超过审查时的可用内存 58 GB。这个数字是估算，没有实测。改用 LoRA 后基本不再是问题。

## 四、执行顺序

1. 决定第 1、2、4 项，按需要修改提示词。
2. 按第 5 到 7 项显式写好训练配置。
3. 用初始模型生成一批回答，经奖励服务计算各分量，确定 τ 和权重（第 3 项），并测量奖励吞吐量。
4. 在本机用小模型验证 LoRA 训练和奖励计算（第 8 项）。
5. 在 H100 上启动训练，奖励通过端口转发由 gbc1 计算。

## 五、已知问题，暂不处理

| 问题 | 说明 |
|---|---|
| 噪声底随物体变化 | 形状完全相同时距离也不为 0，这个常数取决于表面积和包围盒大小的比值。奖励的绝对值不能跨物体比较，训练曲线上的平均奖励会受批次组成影响。GRPO 组内比较基本不受影响（[第 6 步](learn/step6_sampling.md)） |
| 组内标准化放大噪声 | 一组回答的差别只来自采样噪声时，除以组内标准差会把噪声放大成 ±1 量级的优势值。训练后期才会出现（[第 9 步](learn/step9_reward.md)） |
| 生成代码不隔离运行 | 奖励服务以运行用户的身份执行生成的代码，能读写文件、访问网络。决定不做隔离，因为服务已经运行在容器中。剩余风险是奖励作弊：如果某次采样的代码在磁盘上找到并导入了目标 GLB，就会拿到接近满分的奖励，并被训练强化。训练时应抽查得分异常高的回答 |
| 奖励吞吐量 | 13 个请求并发、`max_parallel: 6`、Cycles 64 次采样时，墙钟时间 46 秒，约 0.28 个回答每秒。数据集原脚本是较重的程序化生成代码，模型生成的代码可能更轻。需要用真实回答测量后，再调整并行数、采样数和渲染器 |
| 导出与渲染范围不一致 | `export_mesh.py` 只导出 MESH 类型的对象，`render.py` 还会渲染曲线、曲面、文字和元球。用曲线建模的部件会出现在渲染图里，但不参与 Chamfer 和 Uni3D 的计算 |
| 渲染失败会停止训练 | 网格有三角面但渲染失败时，奖励服务返回 HTTP 500 并发送一次 critical 级别的 Bark 推送，训练随之停止，由人查看日志判断原因。生成的脚本本身也可能导致渲染失败（例如注册了在渲染时报错的回调，或者场景大到渲染时显存不足），这种情况本应算模型的错，但同样会停止训练。目前未见此类情况，出现后再按日志区分。渲染超时仍算作模型的 `timeout` |
| 命令行参数的隐式约定 | `import_glb.py` 和 `export_mesh.py` 共用命令行参数，各自按位置读取。目前正确，不建议改 |
